# VK-only signed Lava invoice creation bridge (2026-11-11)

## Sources of truth / security
- Native `tanyavk` PR #80 released to production SHA `0e12eb6566e6942b22ece66b472c4e5c6fb9dc64`. Native owner-specific HMAC-only POST `/internal/v1/miniapp/users/<actual vk id>/commerce/invoices` performs an atomic claim `(owner, client_request_id)`, makes exactly one provider call, stores provider invoice ID and allowed HTTPS URL, never credits the wallet before the verified webhook. Unknown/timeout → durable `unknown`, no blind retry.
- Main API requires a **VK-only validated bearer** at `POST /mini-app/api/account-preview/vk-invoice`; never reads VK identity or Telegram ID from browser body/query. It signs one exact-body loopback POST for the authenticated VK actor, validates native result and provider checkout URL. No TG actor fallback. The main flag `VK_MINIAPP_CHECKOUT_ENABLED=1` must be enabled **in addition to** native `VK_MINIAPP_PAYMENTS_ENABLED=1` for checkout availability. Both default off.
- VK read-only commerce response reports `payments_enabled=true` ONLY when both independent runtime gates are true. The browser cannot enable it. Frontend checkout appears only for true and only for packages with native Lava offers, with email and card/SBP choices coming from native package config. There are no hardcoded prices, bonuses, or external provider keys. Browser never claims a payment is complete merely after receiving an invoice URL.
- Browser generates a cryptographically strong idempotency key only when explicitly submitting, keeps the key and its exact package/method/email payload across network failure, retry, and navigation away from/back to `Мои работы`; changes in amount/method/email create a new explicit request. Ready → explicit user-click payment link; status paid only after native confirmed ledger. Provider URL is HTTPS validated on native and main server.
