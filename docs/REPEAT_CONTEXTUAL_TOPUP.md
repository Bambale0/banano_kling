# Контекстное пополнение бананов при повторе видео

Статус: реализация в отдельной ветке, выпуск только после обязательных CI и production smoke.

## Пользовательский сценарий

1. Пользователь открывает повтор опубликованного видео или видео-тренда, выбирает свои референсы и параметры.
2. Редактор показывает стоимость в **бананах**, остаток и нехватку. При входящих видеореференсах предложение появляется **только после подтверждения стоимости серверной quote**, учитывающей длительности.
3. Рядом доступно «Купить N🍌 за X ₽» для самого дешёвого действующего одиночного пакета, покрывающего **недостающие**, а не все бананы. «Выбрать другой пакет» показывает реальные альтернативы. Валюта и начисляемые единицы всегда указаны отдельно: например, 150 ₽ не равны 150🍌.
4. Кнопка открывает уже существующее окно пополнения баланса, поднимая выбранный пакет наверх. Пользователь самостоятельно выбирает доступный платёжный способ; никакая генерация, выставление счёта или списание не происходят автоматически.
5. После оплаты пользователь может нажать «Проверить зачисление бананов» (а также работает периодический authenticated bootstrap), закрыть окно пополнения и **самостоятельно** запустить видео. При возвращении в ту же открытую Mini App введённые параметры/загруженные референсы не сбрасываются. Если стоимость изменилась, действующая серверная проверка quote/quote_hash отклонит устаревший запуск.

## Данные и инварианты

- Единственный источник каталога: `payment_packages` авторизованного `/mini-app/api/bootstrap` (runtime-конфигурация пакетов/админка). `mockAppState.paymentPackages` больше не используется для живого/заблокированного checkout. Отсутствующие пакеты => сообщение «Пакеты временно недоступны», **без кнопки покупки**.
- Рекомендация: `shortage = max(0, quote.cost - confirmed_balance)`; выбор по минимальной цене `price_rub` среди пакетов, у которых `credits + bonus_credits >= shortage`. Промо-бонус не обещается заранее: размер определяет сервер в `create-payment` по доступному промокоду и правилам. Витрина не создаёт произвольных `package_id`.
- При нехватке более самого большого пакета не появляется ложная рекомендация «достаточно одного»; предлагается просмотреть все пакеты. Если пользователь вручную выбирает недостаточный пакет, в окне пополнения он помечается предупреждением.
- Бананы начисляет только существующий серверный платёжный путь после подтверждения провайдера. Клиентские действия после оплаты лишь запрашивают `bootstrap`; они **не меняют** баланс локально и не инициируют повторно платёж.
- Для WAN 3 применяется одобренный серверный `reserve_cost`; для Kling 4 — подтверждённая серверная `charge_cost`; для Seedance 2.5 / обычных повторов и трендов с видео — соответствующая проверенная quote. Серверные auth, pricing hash, charge/refund, reconciliation, webhook idempotency, промо/реферальные начисления остаются нетронутыми.
- Скрытые промпты остаются в серверной публикации, не записываются в storage ради пополнения. Контекст оплаты содержит только стоимость и `packageId`, без текста/URL референсов и user_id. Повторный запуск только с явным согласием.

## UX и ограничение восстановления

- Окно оплаты монтируется в `document.body`, выше открытого модального редактора тренда. Если асинхронный `window.open` заблокирован, есть **отдельная кликабельная** ссылка «Перейти к оплате» как для Robokassa/Lava/KASSA, так и для Stars и Tribute. Основной WebView не перенаправляется, чтобы не терять форму.
- Во время ожидаемого API-запроса создание второго счёта заблокировано. После ответа предыдущая ссылка доступна для продолжения оплаты, но **явное повторное нажатие** на способ оплаты может создать свежий invoice для повторной покупки/истёкшего счёта. При закрытии пополнения устаревшая ссылка очищается. Успех Stars и ошибка обновления баланса сообщаются раздельно; повторную покупку после подтверждённой оплаты не предлагаем.
- Состояние повтора сохраняется **пока Mini App остаётся открытой в том же WebView**. При реальной выгрузке процесса iOS, явной перезагрузке страницы или закрытии Mini App черновик с несохранёнными локальными полями может исчезнуть. Persisted server-side draft/resume с версионированием и TTL — отдельная задача; не следует обещать сохранение после hard reload без этой реализации.
- Genjutsu использует собственную систему рецептов/запусков и пока не подключён к общему предложению; стандартные видеоформы, Seedance 2.5, WAN 3 и Kling 4 покрыты текущей задачей.

## Проверки и релиз

- Jest: `lib/__tests__/generation-funding.test.ts`; `components/__tests__/generation-funding-offer.test.tsx`; `components/__tests__/balance-sheet-payment.test.tsx`; `components/forms/video-generator-form-repeat-pricing.test.tsx`.
- Browser E2E: `e2e/critical-flows.mjs` включает simulated trend → серверную цену → недостаток → пакет → invoice → authenticated balance confirmation → ручной запуск с исходным reference URL и quote_hash. Все платёжные и генерационные ответы в этом тесте **моки** (ни одной реальной оплаты или генерации).
- Перед merge требуются `npm run lint`, `npm test`, `npm run build`, Playwright browser E2E и 4 обязательных CI check contexts, а также review; релиз идёт штатным автодеплоем с `tanyapi`, затем проверка точного SHA, backend health, статического frontend revision и не платного production smoke.
- Миграций БД, новой экономической конфигурации, изменений backend pricing/webhook нет. Откат — revert PR в `tanyapi`, со штатным CI/CD.
