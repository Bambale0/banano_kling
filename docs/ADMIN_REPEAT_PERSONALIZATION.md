# Персонализация повторов опубликованных работ — публичный доступ и admin preview

Функция относится к обычным опубликованным фото и видео. Она не меняет существующую персонализацию трендов и не меняет правила загрузки фотографий.

## Включение

Публичный доступ управляется отдельным флагом `REPEAT_PERSONALIZATION_PUBLIC_ENABLED` (по умолчанию выключен).
Значения `1`, `true`, `yes`, `on` открывают функцию всем авторизованным пользователям:
настройку своих публикаций, загрузку вариантов и использование вариантов при повторе.
Право администратора не даёт пользователю право редактировать чужую работу: сервер проверяет владельца.

При выключенном публичном флаге сохраняется прежний режим: `REPEAT_PERSONALIZATION_ADMIN_PREVIEW_ENABLED`
и серверная проверка `config.is_admin(telegram_id)`. При обоих выключенных флагах структурированные запросы
отклоняются до списания и провайдера; обычный свободный повтор продолжает работать.

Клиентский `isAdmin` не управляет доступом. Для собственных файлов сохраняются проверка владельца,
лимиты выбранной модели, проверка публикации и транзакционная проверка изменений перед списанием.
Публичный запуск не делает генерации бесплатными: применяются действующие тарифы, quote и idempotency.

Для обратимого выключения публичного доступа достаточно вернуть публичный флаг в `0` и штатно
пересоздать backend с новым окружением. Приватные исходные фрагменты получает только владелец
через редактор, а повторяющий получает подписи и варианты без исходного текста.

## Контракт

В настройках публикации автор задаёт до шести пар:

- видимое название, например `Одежда` или `Предмет`;
- **только для текстового параметра:** точный исходный фрагмент приватного prompt, например `blue coat` или `chocolate cake`. Для параметра с изображениями достаточно названия группы и вариантов.
- до 12 готовых вариантов, которые человек выбирает одним нажатием; если варианты не заданы, остаётся ограниченный текстовый ввод.

### Варианты с изображениями

В редакторе публикации у каждого текстового параметра можно загрузить до 12 изображений
и задать им названия. Такие варианты показываются сеткой из трёх колонок с рамкой
выбранной плитки. Названия групп задаёт автор (например, «Наряд девушки» или «Машина»).
Опция «Разрешить загрузить свой вариант» добавляет плитку загрузки собственного фото.
Картинки и текстовые кнопки в одном параметре не смешиваются. Названия групп с изображениями должны быть уникальными без учёта регистра, чтобы инструкции для модели не конфликтовали. У группы с изображениями поле исходного фрагмента скрыто: сервер **не ищет** название группы или старое `original_value` в приватном промпте. Название задаёт роль референса (например, «Образ», «Торт», «Машина»).

Контракт поля: `image_choices: [{id, label, image_url}]`, `allow_custom_image: boolean`.
Клиент отправляет в `repeat_user_values` идентификатор варианта либо `upload:<url>`
своего авторизованного image-reference. Сервер проверяет владельца собственного файла,
выбирает каталог по сохранённому ID и добавляет изображения после восстановления
исходных референсов. Для каждой группы сервер добавляет к полному исходному промпту отдельную
приоритетную инструкцию «используйте @ImageN для этой детали» без поиска и замены
исходных слов. Сохранённые исходные референсы остаются на своих местах, а
каждый выбранный референс получает реальный индекс после дедупликации:
например @Image1 — лицо, @Image2 — одежда, @Image3 — торт, @Image4 — машина
(фактические индексы вычисляются из provider payload, а не задаются вручную).
Одинаковые выбранные изображения используют один номер. Текстовые поля
по-прежнему заменяют проверенные точные исходные фрагменты. Остальной сценарий
и исходные медиа сохраняются. Пользовательский ввод не управляет URL готовых вариантов.

Загрузка `file_kind=repeat_choice_image` требует авторизации и разрешения функции через публичный флаг либо админское превью. Файл декодируется и сохраняется JPEG в
`static/uploads/repeat-choices/`, отдельно от личных SavedReference и их retention.
Загрузки не опубликованных или удалённых вариантов автоматически не удаляются.
При недоступном файле или превышении лимита модели запрос отклоняется до запуска.

Видеоварианты используют режим референсов: Seedance 2.0, мультимодальный Seedance 2.5,
Gemini Omni Video; WAN поддерживает режимы reference/edit. В режимах отдельных кадров
и несовместимых видео-моделях выбор изображений отклоняется до списания, чтобы модель
не проигнорировала выбранный вариант. Настройки разрешения и стоимость остаются штатными.
Текстовые параметры и существующие повторы без новых полей работают по прежнему контракту.

Привязки `original_value` **только для текстовых полей** хранятся в отдельной таблице `generation_repeat_personalization`, создаваемой штатной инициализацией БД, и доступны только владельцу через авторизованный редактор. У графических групп прежние сохранённые `original_value` игнорируются при чтении и повторном сохранении. Карточки повтора получают только ключ, подпись, варианты, тип и ограничения — без исходного фрагмента и без скрытого prompt. Совпадающие и вложенные исходные фрагменты отклоняются до публикации, чтобы одна замена не уничтожала привязку другой.

При запуске сервер:

1. заново загружает приватный prompt непосредственной опубликованной работы;
2. проверяет доступ к функции, публикацию, известные ключи и обязательные значения;
3. заменяет только разрешённые автором точные фрагменты **текстовых** полей;
4. для групп изображений добавляет приоритетные инструкции с фактическими `@ImageN` без анализа исходного текста; сохраняет полный сценарий и добавляет свободное уточнение через существующий remix-компоновщик;
5. независимо восстанавливает разрешённые фото/видео-референсы по существующему серверному контракту.

Снятие публикации всегда логически очищает её настройку персонализации, даже если preview позднее выключен, поэтому скрытая конфигурация не воскреснет после повторного включения. При повторной публикации без переданного поля существующая настройка сохраняется; явный пустой список очищает её. Каждая запись и очистка получают уникальный `write_token`; предыдущая конфигурация читается и новая ревизия записывается в одной транзакции. SQLite сериализует запись через `BEGIN IMMEDIATE`, а PostgreSQL сначала блокирует строку исходной генерации `FOR UPDATE`, поэтому параллельные изменения одной работы видят актуальную предыдущую ревизию. Если публикация не удалась, компенсация применяется только к той же ревизии, поэтому запоздавшая ошибка не может перезаписать более новую успешную настройку — даже с идентичными значениями. При выключенном флаге остальные публичные операции новую таблицу не изменяют.

## Проверка перед релизом

- публичный флаг выключен: остаётся прежнее админское превью; оба флага выключены — новые поля не выдаются;
- при публичном флаге обычный автор настраивает только свои работы, а повторяющий выбирает значения; чужая настройка отклоняется;
- админская карточка не содержит `original_value` и текст приватного prompt;
- фото и видео получают полный базовый prompt, точные замены и свободное уточнение;
- исходные разрешённые референсы доходят в provider payload без передачи URL в скрытый DTO;
- переполнение provider prompt отклоняется до списания, существующие legacy/typed/owner повторы остаются зелёными.

Флаг не включается автоматически миграцией или выкладкой. Для production требуется отдельное разрешение, точный SHA, штатный deploy и smoke-проверка.

## Исправления проверки PR #382

Установленные обработчики ленты и профиля прикрепляют безопасные поля после проверки доступа к функции. Редактор переносит сохранённую конфигурацию в task detail, поэтому закрытие/повторное открытие и последующее изменение публикации не восстанавливают старые значения.

Для WAN 3 и WAN Prime поля выдаются через авторизованный repeat-plan. Выбранные значения входят в замороженный client recipe и quote, сервер компилирует их в приватный prompt до добавления свободного уточнения. Разрешённые исходные медиа и нумерованные замены сохраняются. Структурированные значения вне опубликованного повтора, при отсутствии доступа к функции отклоняются до media probe, billing и provider. Перед резервированием транзакция повторно проверяет отпечаток конфигурации.

Полное скрытие из HTTP, Telegram profilehide и админского feed/remove очищает существующие поля в общей транзакции снятия публикации. PostgreSQL соблюдает единый порядок блокировок: generation, затем personalization. Перенос из общей ленты в профиль полей не удаляет. Варианты проходят ту же проверку типа, что и значения при повторе: например, возраст должен быть числом.

## Тексты публичного интерфейса
В редакторе и формах повторов используются понятные описания действий без упоминаний серверов, приватных рецептов и админского превью. Файлы подписаны «Фото», «Видео», «Аудио». В редакторе, выборе изображений и личной библиотеке сырые HTTP/provider/URL/служебные ошибки заменяются безопасным сообщением, а понятная проверка файла сохраняется. Технические данные остаются в диагностике и внутреннем контракте.

## Разделение референсов автора и личных фото при повторе видео

Авторские готовые варианты (например «Машина», «Одежда», «Торт») — это отдельные группы для выбора из изображений. Они **не** являются обязательными загрузками посетителя и **не** используют личную библиотеку автора. Пользовательские фото (лицо, фото пары и другие собственные материалы) выбираются в отдельных полях, через загрузку или свою библиотеку. Привычный способ создавать видео с несколькими личными референсами остаётся самостоятельным и не меняется.

В мультимодальной опубликованной работе готовая группа может занимать одно заменяемое место исходного фото, не добавляя вторую копию файла в провайдерский запрос. Например, когда автор использовал четыре исходных фото и подготовил три группы вариантов, пользователь увидит только **одно** обязательное место для своего фото и три сетки готовых вариантов. Для сюжета с парой свободных позиций может быть две. Система не устанавливает универсальное требование загружать 4 фото: количество определяется исходным сценарием, явно сохранёнными разрешениями автора и настроенными группами.

В редакторе публикации автор может отдельно выбрать, какое исходное фото заменяет каждая группа. Без явной привязки группы используют последние доступные заменяемые фото по порядку. Первые незанятые позиции остаются для личных фотографий. Нельзя назначить две группы на одну позицию или перезаписать референс, который автор явно разрешил использовать без замены. Указанные номера используются сервером при формировании точных `@ImageN`; посетителю исходные изображения, фрагменты промпта и внутренние привязки не выдаются.

При отсутствии таких групп продолжает работать старый режим загрузки референсов. Для старых сценариев, в которых каталог невозможно совместить с существующими заменяемыми позициями, остаётся прежняя механика дополнительного изображения; модельные лимиты и списание проверяются как раньше. Публичный флаг и проверки владельца сохраняются.


## Проверка привязок при сохранении публикации

Для видео сервер проверяет совместимость вариантов с выбранными разрешениями на исходные фото до сохранения настроек. Две группы не могут занимать одно фото, а закреплённый исходник не может одновременно заменяться вариантом. Проверка действует и при изменении разрешений без изменения самих групп; некорректный запрос возвращает 400 и сохраняет прежнюю публикацию.

При выборе фото для группы редактор снимает разрешение на неизменяемое использование этого исходника. Уже занятое другой группой фото недоступно в списке. Личные фото посетителя остаются в свободных позициях, остальные разрешённые референсы не меняются.
