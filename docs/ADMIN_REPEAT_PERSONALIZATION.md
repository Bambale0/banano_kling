# Персонализация повторов опубликованных работ — admin preview

Функция относится к обычным опубликованным фото и видео. Она не меняет существующую персонализацию трендов и не меняет правила загрузки фотографий.

## Включение

Флаг `REPEAT_PERSONALIZATION_ADMIN_PREVIEW_ENABLED` по умолчанию выключен. Значение `1`, `true`, `yes` или `on` включает превью, но сервер всё равно проверяет `config.is_admin(telegram_id)` отдельно для:

- настройки полей автором при публикации;
- выдачи безопасных полей в карточках ленты/профиля и deep link;
- отправки выбранных значений в повтор фото или видео.

Одного клиентского `isAdmin` недостаточно. При выключенном флаге или для не-админа структурированный payload отклоняется до биллинга и вызова провайдера. Старый свободный повтор продолжает работать без изменений.

## Контракт

В настройках публикации администратор задаёт до шести пар:

- видимое название, например `Одежда` или `Предмет`;
- точный исходный фрагмент приватного prompt, например `blue coat` или `chocolate cake`.
- до 12 готовых вариантов, которые человек выбирает одним нажатием; если варианты не заданы, остаётся ограниченный текстовый ввод.

### Варианты с изображениями

В редакторе публикации у каждого текстового параметра можно загрузить до 12 изображений
и задать им названия. Такие варианты показываются сеткой из трёх колонок с рамкой
выбранной плитки. Названия групп задаёт автор (например, «Наряд девушки» или «Машина»).
Опция «Разрешить загрузить свой вариант» добавляет плитку загрузки собственного фото.
Картинки и текстовые кнопки в одном параметре не смешиваются.

Контракт поля: `image_choices: [{id, label, image_url}]`, `allow_custom_image: boolean`.
Клиент отправляет в `repeat_user_values` идентификатор варианта либо `upload:<url>`
своего авторизованного image-reference. Сервер проверяет владельца собственного файла,
выбирает каталог по сохранённому ID и добавляет изображения после восстановления
исходных референсов. Разрешённый фрагмент промпта заменяется привязкой к реальному
`@ImageN`; одинаковые выбранные изображения используют один номер. Остальной сценарий
и исходные медиа сохраняются. Пользовательский ввод не управляет URL готовых вариантов.

Админская загрузка `file_kind=repeat_choice_image` требует тот же feature flag и
серверную проверку администратора. Файл декодируется и сохраняется JPEG в
`static/uploads/repeat-choices/`, отдельно от личных SavedReference и их retention.
Загрузки не опубликованных или удалённых вариантов автоматически не удаляются.
При недоступном файле или превышении лимита модели запрос отклоняется до запуска.

Видеоварианты используют режим референсов: Seedance 2.0, мультимодальный Seedance 2.5,
Gemini Omni Video; WAN поддерживает режимы reference/edit. В режимах отдельных кадров
и несовместимых видео-моделях выбор изображений отклоняется до списания, чтобы модель
не проигнорировала выбранный вариант. Настройки разрешения и стоимость остаются штатными.
Текстовые параметры и существующие повторы без новых полей работают по прежнему контракту.

Привязки `original_value` хранятся в отдельной таблице `generation_repeat_personalization`, создаваемой штатной инициализацией БД, и доступны только владельцу через авторизованный редактор. Карточки повтора получают только ключ, подпись, варианты, тип и ограничения — без исходного фрагмента и без скрытого prompt. Совпадающие и вложенные исходные фрагменты отклоняются до публикации, чтобы одна замена не уничтожала привязку другой.

При запуске сервер:

1. заново загружает приватный prompt непосредственной опубликованной работы;
2. проверяет флаг, администратора, известные ключи и обязательные значения;
3. заменяет только разрешённые автором точные фрагменты;
4. сохраняет весь остальной сценарий и добавляет свободное уточнение через существующий remix-компоновщик;
5. независимо восстанавливает разрешённые фото/видео-референсы по существующему серверному контракту.

Снятие публикации всегда логически очищает её настройку персонализации, даже если preview позднее выключен, поэтому скрытая конфигурация не воскреснет после повторного включения. При повторной публикации без переданного поля существующая настройка сохраняется; явный пустой список очищает её. Каждая запись и очистка получают уникальный `write_token`; предыдущая конфигурация читается и новая ревизия записывается в одной транзакции. SQLite сериализует запись через `BEGIN IMMEDIATE`, а PostgreSQL сначала блокирует строку исходной генерации `FOR UPDATE`, поэтому параллельные изменения одной работы видят актуальную предыдущую ревизию. Если публикация не удалась, компенсация применяется только к той же ревизии, поэтому запоздавшая ошибка не может перезаписать более новую успешную настройку — даже с идентичными значениями. При выключенном флаге остальные публичные операции новую таблицу не изменяют.

## Проверка перед релизом

- флаг выключен: публичные DTO и формы не меняются;
- не-админ не может настроить или отправить `repeat_user_values`;
- админская карточка не содержит `original_value` и текст приватного prompt;
- фото и видео получают полный базовый prompt, точные замены и свободное уточнение;
- исходные разрешённые референсы доходят в provider payload без передачи URL в скрытый DTO;
- переполнение provider prompt отклоняется до списания, существующие legacy/typed/owner повторы остаются зелёными.

Флаг не включается автоматически миграцией или выкладкой. Для production требуется отдельное разрешение, точный SHA, штатный deploy и smoke-проверка.

## Исправления проверки PR #382

Установленные обработчики ленты и профиля прикрепляют безопасные поля после проверки флага и администратора. Редактор переносит сохранённую конфигурацию в task detail, поэтому закрытие/повторное открытие и последующее изменение публикации не восстанавливают старые значения.

Для WAN 3 и WAN Prime поля выдаются через авторизованный repeat-plan. Выбранные значения входят в замороженный client recipe и quote, сервер компилирует их в приватный prompt до добавления свободного уточнения. Разрешённые исходные медиа и нумерованные замены сохраняются. Структурированные значения вне опубликованного повтора, для не-админа или при выключенном флаге отклоняются до media probe, billing и provider. Перед резервированием транзакция повторно проверяет отпечаток конфигурации.

Полное скрытие из HTTP, Telegram profilehide и админского feed/remove очищает существующие поля в общей транзакции снятия публикации. PostgreSQL соблюдает единый порядок блокировок: generation, затем personalization. Перенос из общей ленты в профиль полей не удаляет. Варианты проходят ту же проверку типа, что и значения при повторе: например, возраст должен быть числом.

## Ввод вариантов на iPhone (Telegram Mini App)

Поле «Варианты» в редакторе публикации сохраняет свободный ввод с русской
клавиатуры и других IME. Во время набора нативный HTML-input управляет текстом;
React не заменяет вводимый фрагмент при каждом повторном рендере. Значения
синхронизируются после обычного `change`, завершения `compositionend` и
при `blur` перед нажатием «Сохранить публикацию». Последний `blur` нужен
для Telegram WebView на iOS, где финальный `input` после композиции может
не прийти. Разбор по запятым/переносам, максимум 12 вариантов, исходный скрытый
prompt и права администратора не меняются.

Регрессия: `frontend/miniapp-v0/components/__tests__/task-detail-publication-references.test.tsx`:
текст «платье, костюм» должен сохраниться, даже если после `compositionend`
не было отдельного события `change`. Реальную клавиатуру iPhone необходимо
проверить дополнительно после выкладки.
